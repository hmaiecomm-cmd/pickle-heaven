## 架构决策

### 为什么选择 SSE 而不是 WebSocket？

| 特性 | WebSocket | SSE |
|---|---|---|
| 兼容性 | 需要特殊支持 | HTTP 标准 |
| 无服务器 | 困难 | 原生支持 |
| 实现复杂度 | 高 | 低 |
| 双向通信 | 支持 | 单向（足够） |
| **选择** | — | ✅ **Vercel 推荐** |

### 异常推送流程

```
1. 客户端建立 SSE 连接
   ↓
2. 服务器维持长连接并发送心跳
   ↓
3. 异常系统检测到事件
   ↓
4. 服务器通过 SSE 推送异常
   ↓
5. 客户端接收并触发回调
   ↓
6. DeviceManager 智能刷新当前迴路
```

## 已知限制

1. **演示异常生成**
   - 当前 SSE 端点使用 Demo 异常（5% 概率）
   - Phase 6d 中将串接真实异常源

2. **单向通信**
   - SSE 只支持单向推送（服务器 → 客户端）
   - 足够满足异常推送需求
   - 可靠性高于 WebSocket

3. **Vercel 限制**
   - 无服务器环境连接有时间限制
   - SSE 长连接可能在 600 秒后断开
   - 客户端需实现重连逻辑
